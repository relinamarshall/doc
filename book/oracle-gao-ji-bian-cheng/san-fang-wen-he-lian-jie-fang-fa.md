# 三、访问和联结方法

优化器必须确定如何来访问你的SQL语句所需要的数据。你构造SQL语句，而优化器则在硬解析的过程中算出哪些运算能够尽可能高效地提供数据。主要根据统计信息，优化器将会计算各个备选项首先访问数据然后进行多表联结以获取最终数据集的成本。你对优化器可能会考虑的不同访问和联结方法了解得越多，就越能够构造出恰当的SQL语句来帮助优化器作出最好的选择。并且，当优化器所选择的运算不能满足你的性能需求时，你可以更准确地来确定哪些运算更适合 提供你想要的响应时间。

在SQL语句的表达式和条件均评估完毕，以及所有可能有助于更准确地生成执行计划的查询转换都进行完以后，生成执行计划的下一个步骤就是利用优化器来确定访问数据的最好方法。一般来说，总共只有两种基本的数据访问途径:**全扫描**或者**索引扫描**。在全扫描(顺便说一下，可能是**全表扫描**，也可能是**快速全索引扫描**)过程中，多个块被读入到一个I0运算中。**索引扫描**首先扫描索引叶子块以取得特定的行id，然后利用这些行id来访问父表取得实际的行数据。这些访问都是通过单块读取来完成的。如果在数据表访问的步骤之后还需要进一步的数据选，这些行将会在被包含在最终结果集之前通过筛选。&#x20;

某个表所选定的访问方法被用来确定最终计划中所使用的表联结方法和联结顺序。因此，如果为某个表选择的访问方法并不是最优的，整个执行计划不完美的可能性也就相应更大。统计信息在优化器准确确定最优方法的过程中扮演了关键的角色。与典型的统计信息一起,优化器将利用你的查询来算出你需要多少数据以及哪种访问方法能够尽可能快地提供数据。查询中的每个表都会首先被独立评估以确定它的最佳访问途径。下面将详细讲解各种访问方法。

## 全扫描访问方法

当对一个对象进行全扫描时，与该对象相关的所有数据块都必须取出并进行处理，以确定块中所包含的数据行是否是你的查询所需要的。请记住Oracle必须将整个数据块读取到内存中以取得这个块中所存储的数据行的数据。**因此，当发生全扫描时，实际上优化器(还有你)需要考虑两件事:必须读取多少个数据块以及每个数据块中有多少数据将被舍弃**。此时此刻我想要让你理解的是，确定全扫描是否是正确选择并不仅仅基于查询将会返回多少行。有很多已发表的“经验法则”会这样说:“如果你的查询将会取出表中多于x%的数据行，则应该选择全扫描。”除了这些经验法则(ROT，Rule Of Thumb=ROT)以外还有很多要考虑的，不要被这些法则束缚着而忽略了为了做出正确选择而需要考虑的其他方面。我并不是说经验法则背后的原理在逻辑上没有意义，而只是说需要考虑的事情并不仅限于此。当一个查询需要返回表中绝大多数的数据行时，选择使用全扫描的可能性当然也是很高的,但这个普遍规则的问题在于所返回行数的比例在某种程度上是任意的。在这些年中，这个法则在不同的书籍、论文以及论坛中都出现过，而这个比例从20%\~70%都有。为什么它要变呢?

### 如何选择全扫描操作

全表扫描选择规则所存在的问题，它不仅仅是与数据行有关，还与数据块以及丢弃有关。将所有这些方面的信息集合起来，就会得出全表扫描是否有意义的结论，即使返回的数据行百分比可能很小。另一方面，即使返回的数据行百分比很高也有可能不应该选择全表扫描。看下面例子，看看即使查询仅需要返回很小比例的数据行时，优化器为何也有可能选择全表扫描执行计划。首先，创建了两个同样的具有10000行数据的表。然后，给出了每张表对于同一个查询的执行计划，注意为什么即使查询仅返回100行(只有总数据量的1%)也会选择全表扫执行计划。

> 创建两个测试表

<pre class="language-sql" data-title="SQLPlus" data-line-numbers><code class="lang-sql">create table t1 as
select trunc((rownum-1)/100) id,rpad(rownum,100) t_pad
from DBA_SOURCE where rownum &#x3C;= 10000;

create index t1_idx1 on t1(id);

--收集表t1统计信息
<a data-footnote-ref href="#user-content-fn-1">exec dbms_stats.gather_table_stats(user,'t1',method_opt=>'FOR ALL COLUMNS SIZE 1',cascade=>TRUE);</a>

create table t2 as
select MOD(rownum,100) id,rpad(rownum,100) t_pad
from DBA_SOURCE where rownum &#x3C;= 10000;

create index t2_idx1 on t2(id);

--收集表t2统计信息
exec dbms_stats.gather_table_stats(user,'t2',method_opt=>'FOR ALL COLUMNS SIZE 1',cascade=>TRUE);
</code></pre>

每个表都有10000行数据。两个表中的id列对于0\~99的每个值都有100行。因此，从数据内容的角度来说,这两张表是一样的。但是,注意对于T1,id列是通过表达式`trunc((rownum-1)/100)`来计算的，而T2中的id列则使用`mod(rownum,100)`计算。下图展示出了表中的数据块是如何进行物理存储的。

<figure><img src="../.gitbook/assets/image (21).png" alt=""><figcaption><p>随机存储与顺序存储数据行值对比图</p></figcaption></figure>

对于刚插入这两张表中的数据，如果执行一个查询来获取任何一个值,都可以预料到结果集中将会有100行。如果通过查询实际数据来确定结果集的大小是合理的，那么对于了解从查询中可以得到什么而言，这种方法是非常有用的。对于包含在你的查询中的每一个表,你都可以执行一个应用相应谓语的独立查询来估算该表返回的数据行数。这将有助于你估算哪种访问方法最适合你最终的查询。但是，知道行计数只是你所需要的信息的一部分。现在，你需要回到数据是如何存储这个问题上去。

对于每个表中的10000行，如果你查询单个值(whereid=1)，你知道自己将重新得到100行，这只是总行数的1%。对于这么小的百分比来说，你也将预期优化器会选择使用id列的索引来访问数据行，对吗?这看上去似乎是很符合逻辑的结论，但此时正应该去了解一下数据是如何存储的。如果数据是顺序存储的，大多数的id=1的行在物理上仅存储于几个数据块中，如本例中的T1那样，那么这个结论是对的。

## 小结

[^1]: 含义解释

    * `EXEC`: 这是 SQL\*Plus 和 PL/SQL 中用于执行命令的关键字。它是 "EXECUTE" 的简写形式。
    * `dbms_stats.gather_table_stats`: 这是调用 Oracle 数据库中的 `DBMS_STATS` 包中的 `GATHER_TABLE_STATS` 过程，它用于收集表的统计信息。这些统计信息包括行数、列的分布情况、索引情况等。
    * `USER`: 这是一个伪列，用于获取当前用户的名称，作为参数传递给 `GATHER_TABLE_STATS` 过程，表示收集当前用户的表的统计信息。
    * `'t2'`: 这是要收集统计信息的表的名称。
    * `method_opt=>'FOR ALL COLUMNS SIZE 1'`: 这是收集统计信息的选项之一，指定了收集所有列的统计信息，并且为每列指定了采样大小为 1。这意味着对于每个列，只会采样一个值来获取统计信息。这种方法适用于大多数情况，因为它能够提供相对较好的性能和准确性。
    * `CASCADE=>TRUE`: 这个选项表示要对从属于指定表的所有索引、分区和相关对象也进行统计信息收集。这样做可以确保在优化查询时考虑到所有相关对象的统计信息。
