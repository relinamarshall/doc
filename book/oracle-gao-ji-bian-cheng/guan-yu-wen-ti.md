# 关于问题

“那并不是关于查询的，而是关于问题的。”这是在谈到写SQL语句的时候我最喜欢说的一句话。不管你水平如何，要想写好SQL语句,善于提问的重要性与查询本身的重要性几乎是相当的。

在书写SQL语句的时候，问题的重要性体现在很多方面。首先，理解查询背后的问题往往比查询语法本身更重要。如果从SQL语句想要去回答的问题入手，你就能够更仔细考虑并理解如何写出最佳的查询来得到想要的结果。其次，能够提出好的问题以便弄清楚SQL想要做什么并且搜集你需要的所有相关信息，对于写出语法正确而且非常高效的SQL语句是非常关键的。最后，你必须能够很好地建立逻辑表达式来帮助回答SQL背后的问题。

在本章中，我将讲述如何着手来收集你所需要的所有信息以便写出最好的查询。要想做到这一点，你就必须多问好问题。不管你是要写一段新的SOL语句还是修改已有的语句，问题都是过程中最关键的核心部分。

## 问出好的问题

问好的问题是一个睿智的习惯。习惯并不是一夜之间养成的。很久以前，我读过一篇文章说要养成一个新的习惯需要21\~28天。然而,2009年发表的一项研究表明形成一个新的习惯实际上平均要66天。并且行为越复杂,该行为培养成习惯所需的时间也就越长。因此，如果你还没有养成问好问题的习惯，那么一定要明白它需要你付出特别的努力才能达到运用娴熟的程度。

你可能会奇怪所有这些和写SQL查询有什么关系呢。我相信，知道如何问出好的问题，或者更具体地来说，知道如何通过提问来正确地断定你的SQL语句所要回答的问题，这是你需要养成的一个关键的习惯，前提是如果你真的想使自己的SQL水平更上一层楼的话。

要想写出任何SQL语句，就以一个你需要回答的问题入手。答案将会是从你的数据库的表中取出的一行或多行数据所组成的结果集。最开始，你可能要让问题的答案以样例报告或屏幕显示的形式呈现。还有些时候，你会得到更完整的关于查询所需传递信息的描述。更多时候你所得到的查询描述较模糊而不是很清楚，不过你不要感到惊讶。无论你得到了多少关于所要写的查询的信息，你都需要确定自己问了好问题，从而确保你能全面了解如何才能写出能够高效快速地完成任务的SQL语句。

## 提问的目的

问题有助于你弄清楚需求以及你或者需求提出者所持有的假设。问题还能够帮助你收集证据并弄懂按照某种方法来进行编码的含义或结果等信息。问题好像金子。好吧，我猜你可能会说问题的答案才是金子，但问题是你挖掘金子的工具。&#x20;

为了使提出的问题能够提供写出功能正确、性能优良的SQL查询语句所需信息，你必须能够很好地组织问题。不管你对所要求的编码工作了解多少，或者你自认为了解多少，首先将自己当做一张白纸并虚心多加提问都是很有帮助的。通过这样做，你对细节的了解将更有可能会更进一 层，从而避免做出假设。

很多人认为提问会让他们看上去很无知。我却认为这是非常具有魔力的工具。聪明的、精心准备的问题将会引发别人的思考。当一个人思考时，也就打开了通往新思想、新答案以及新发展潜力的大门。当你向某人，尤其是一个有求于你的人提问时，你也就会让他们知道了你很关注他们的需求，并且你想以最好的方式来满足他们的需求。因为害怕被看做是傻瓜而保持沉默可能更会事与愿违。如果你没有问清楚就交付了一些并不能有效满足需求的东西，那么这对你所造成的负面影响将会比先提问要大得多。

所以，我需要指出的是你应该问问题，即使你只是自问自答。这听起来可能很奇怪，如果你碰巧没有好的资源可支配，你仍然要提问并得出答案。问题的答案必须来自你所做的调查研究，但如果从准备一个很好的问题列表开始，你就能够更明确地指导调查研究。

## 问题的种类

问题的分类有很多。通常来说，问题主要可以被分为**开放**的或**闭合**的。选择哪种问题则取决 于你究竟是想要较长的、更详细的答案还是较短的、有限的答案。

开放式问题的目的是开始一段对话并帮助你集中精力进行交谈。开放式问题的答案往往会提供更多的细节而不是简单地通过“是”或者“否”来回答。以“什么”、“怎么样”、“谁”、“什么时候”以及“为什么”开头的问题都是开放式问题。需要小心地问“为什么”这种问题，因为这种问题听上去好像是质问。记住，提问的目的必须是帮助你获得所需的所有详细信息，而不是将任何人推到对立面。例如，问“为什么某些人总是选择这样来行事?”与“基于什么原理做出了这样的选择?”给人的感觉是完全不同的。即使你发现某些事情有问题或根本就是错的，你也可以直接给出反馈而不必经常问“为什么”这样的问题。

大多数时候，你的问题目标就是挖出事实。客观的开放式问题询问特定的信息并希望得到事实上的答案。然而，你必须注意确认你得到的是事实而不是观点。通过询问某人对于某事的看法这样的主观性问题，你将会得到主观的答案。这两者之间的区别有时可能会很关键。

有一些开放式问题的目的就是通过获取反馈来帮助你获得新想法,尤其是那些关于你需要采取的行动的想法。这些是解决问题型问题。这些类型的问题在进行头脑风暴以获得各种不同的想法时是很有帮助的。你的同事就是这种类型问题的最棒的答案来源。一旦得到了需要的详细信息,请你一定要反馈给其他的开发人员。他们通常会提出一些你可能永远也想不到的解决方案。

在进行SOL开发的时候你应该问的两种最常见的问题是**客观性**的和**解决问题型**问题。下面是一些例子。

* 数据模型是什么?有数据字典或ERD可用吗?
* 如果有的话，其他相关的查询是如何来写的?
* 谁是此类应用的主题专家?
* 这个查询对于响应时间的要求是什么?&#x20;
* 你要如何来实现需求?
* 下一步我要干什么?&#x20;
* 你会建议我去复查哪些内容?

如果你只想得到“是”或“否”的响应或者是很简短的答案，最好使用**闭合式问题**。以“是不是”、“能否”、“是否”等开头的问题将会得到简短而直接的响应。这种类型的问题不能是模棱两可的。如果你实际想得到的答案就是“是”或者“不是”，你需要确定你所问出的问题不会导致得到很长的回应。此类问题就是想要阻止或禁止长篇大论的讨论。闭合式问题可以分为3类:**确认型、选择型，以及是/否型**。当使用确认型问题的时候，你想要得到明确的答案但是并不提供任何选项。选择型问题提供两个或更多的可选项。是/否型问题只要用简单的“是”或“否”来回答。

为了说清这3类问题之间的区别，我将通过3种不同的方式来问同一个问题。

* 确认型:employees表是什么类型的表?&#x20;
* 选择型:employees表是堆表还是索引组织表?&#x20;
* 是/否型:employees表是堆表吗?

在这些类型中，选择型问题是你最需要小心对待的。在这个例子中，我只提供了两个选项:堆表和索引组织表。但如果这个表是一个聚簇表怎么办呢?如果没有把这个选项放在可选列表中，对于最初的问题你最终可能会得到一个是/否的回答。回答这个问题的人可能(粗鲁地)只回答一个“不是”。然后你还必须接着提一个确认型问题来得到你所需要的答案。

选择正确的问题类型几乎和问题本身同样重要。你需要尽快得到所需的详细信息。因此，请记住当你**需要得到简短答案的时候使用闭合式问题**,而**需要引起讨论并得到较为详细答案的时候使用开放式问题**。最常见的错误就是当你实际上需要得到更为详细信息的时候却问了闭合式问题。例如，“你能告诉我关于这个项目的情况吗?”严格来说就是一个用“是”或“否”来回答的闭合式问题。大多数人都已经学会了很礼貌地来回答这样的问题(详细回答)，即使所提问的问题类型是错误的。但实际上提出正确类型和形式的问题以便被问者能够给出适当的答案是提问者的责任。

## 关于问题的问题

写一个新的查询语句通常要比试着去修改别人已经写好的查询更简单。这是因为当你写新的查询语句时，你不必担心如何弄懂别人代码的含义，而真正需要担心的是查询说明。不管这个说明是不是很详细，你都需要确认写出的SQL语句能够给出所处理问题的答案。

让我们来看一个说明这个过程是如何进行的例子。我将扮演使用者的角色而你扮演应用开发工程师的角色。我的需求是写一个能够列出所有在本公司内干过多种工作岗位的员工的查询。我只想让输出展示emp\_id和每个员工干过的岗位总数目。下列代码清单给出了你所写出的能够满足我的需求的查询。

> 列出干过多个工作岗位的员工

{% code lineNumbers="true" %}
```plsql
select emp_id,count(*) job_ct
from job_history
group by emp_id
having count(*) > 1;
```
{% endcode %}

这很简单，不是吗?你完成测试以后就交付了这些代码。但是，我很快回来找你并说代码错了。得出的列表中少了一些干过多个工作岗位的员工。我之前曾经手工生成过这个列表，并且知道下面这些员工应该被包括在列表中:101、102、114、122、176、200和201。

哪儿出错了呢?这看上去是一个相当简单的査询,对不对?它之所以会出错则是因为在给出解决方案之前没有问任何问题。由于没提问，你做了一些假设(不管你是否意识到)。你所做的假设使你写出了上面的查询。你所写的查询并没有得到我所想要的结果。不可否认，我本应该给你更多更详细的说明或者提供我想要的初始结果集来帮你写出正确的查询。不管你得到的查询需求说明质量如何，都不要忘了这样一点，弄清楚详细要求并确定开发的代码确实回答了提出的问题是你的责任。

让我们重新开始。我所提供的查询需求需要写一个能够提供本公司所有干过多种工作岗位的员工列表的查询，需要列出emp\_id和每个人干过几种岗位。乍看上去，查询需求似乎是很直接的，但在简单表象的背后却隐藏着一些玄机，除非你问些问题否则可能意识不到。下面列出了几个你要弄清楚需求本应该问的问题。

* 在查询中将员工当前的工作岗位列入计数还是只考虑除了当前工作岗位以外的岗位?&#x20;
* 能够满足需求的数据存放在哪儿，即在一张还是多张表中?&#x20;
* 数据模型是什么样的?如果有的话,我能否得到一份数据字典或ERD(实体关系图,entity relationship diagram)的副本?&#x20;
* 结果集有预期的典型尺寸吗?&#x20;
* 数据是如何存储的?
* 这个查询有必须满足的响应时间服务水平协议(service level agreement，SLA)吗？
* 这个查询执行的频率如何?

如果你从使用者处收到了一个需求，问他们所有这些问题可能并不可行。问一个使用者他所需要的数据在哪张表中或者你是否可以获得一份ERD的副本可能会让他一脸茫然,因为这些事情通常超出了使用者的知识范畴。需要注意的很重要的一点就是查询的需求是来自于应用程序的用户还是应用程序的架构师。这些问题中有很多只能由能够对应用从技术的角度进行理解的人来回答。因此，当你需要获得详细技术信息的时候首先要搞清楚你面对的人是谁。可能是DBA(数据库管理员，Database Administrator)、数据架构师或者最开始在这个特定应用中从事其他部分编码的开发人员。随着时间的推移，你将建立起能够自己确定这些问题答案的知识体系，但搞清楚谁是你所支持的应用的主题专家总归是好的。

最初的时候，得到前3个问题的答案是最重要的。你必须知道除了查询所需要获取内容以外更多的东西。对数据模型尽可能的熟悉是一个起点。在最开始写查询的时候，做了一个假设，即满足这个查询所需要的数据都存放在job\_history表中。如果问了前3个问题，你就会发现实际上job\_history表就是一个历史表，只包含历史数据而没有当前的数据。在employees表中的job\_id列存放了员工的当前岗位信息。因此，为了确定一个员工干过多少个岗位，你需要从employees表中取出他们的当前岗位并从iob history表中取出历史岗位。

有了这些信息，你就可以像下列代码清单中那样来重写这个查询。

{% code lineNumbers="true" %}
```plsql
select emp_id,count(*) job_ct
from (
    select e.emp_id,e.job_id
    from employees e
    union all
    select j.emp_id,j.job_id
    from job_history j
)
group by emp_id
having count(*) > 1;
```
{% endcode %}

现在看上去结果是正确的了。也就是在这时候下一个问题的答案开始起作用。知道想要什么当然是很重要的，前3个问题帮助我描述清楚了查询所需要返回的数据。大多数的人就止步于此了。然而，知道如何来得到我所想得到的数据同样重要。这与我们大多数人所接受的关于关系数据库的一般理论是相悖的。在大学里我所上的一门关于关系数据库管理系统的课程中，我被告知SQL是用来访问数据的。为了访问那些数据我没必要知道任何关于数据存储在哪儿以及如何存储的内容，或者为了访问这些数据RDBMS(关系型数据库管理系统，Relational Database Management System)是如何来处理SQL语句的。换句话说，SQL就是用来描述将要干什么，而不是如何来干的。

事实是知道你的数据是如何存储和访问的与描述你的查询所取的数据是同样重要的。让我们假设你需要预定从华盛顿到洛杉矶的旅程。你给旅行代理人打电话让他帮你处理预订事宜。如果你所提供给代理机构的信息仅包括出发及到达城市，以及你需要尽可能的便宜的机票，结果会怎么样呢?最便宜的航班可能在早晨5:30离开华盛顿然后分别经停亚特兰大、芝加哥以及达拉斯，最终在午夜到达洛杉矶(洛杉矶当地时间，也就是华盛顿时间的凌晨3点)。你愿意这样吗?可能不愿意。就我个人来说,我更愿意多花点钱来订一个从华盛顿到洛杉矶的直飞航班。仔细想想吧如果你可以乘坐上午8点从华盛顿出发10点到达洛杉矶的直飞航班，是不是要比停好几次并花上将近整整一天的时间在路上对你更有吸引力呢?如果直飞的航班仅比那噩梦般的航程贵出10%呢?你最开始想要订最便宜航班的需求并没有包含在什么条件下你愿意付更多钱。从而，你的要求达到了但是你却并不满意该结果。

知道数据是如何存储的以及应当如何来访问它将会确保你的查询不仅能够返回正确的结果而且能够尽可能快速高效地返回。这就是为什么必须问“一般的预期结果集是多大?”“数据是如何存储的?”及“需要查询执行的速度和频率如何?”等问题。没有这些问题，你的查询可能会得到正确的结果，但仍然因为较差的性能导致失败。仅仅得到正确的结果是不够的。为了能够成功，你的查询不仅要正确还要快速。

## 关于数据的问题

我希望到目前为止你已经认识到你确实有必要关注数据是如何存储的以及应该如何来访问它们了。你从哪儿可以找到这些信息呢?通过执行几个简单的查询，数据库可以给出你所需要的绝大多数信息。你得到这些信息后，需要确定应该如何来访问这些数据。这就需要理解各种访问和联结方法是如何实现的以及在什么情况下适用哪一种方法。我已经讨论过访问和联结方法了，因此你应该已经获得了完成该任务所需的知识。但你如何来发现数据的存储方式呢?让我们来看看在这个过程中，为了得到相应的答案，你需要问的问题和需要执行的查询。

首先第一步,试着像优化器一样去思考问题。优化器需要统计信息和实例参数值来计算计划因此，站在优化器的立场上并收集有助于形成执行计划的信息是个好主意。你应该总是需要找出下面这些问题关于数据的答案。

* 为了得到所需的全部数据都需要哪些表?&#x20;
* 其中有表是分区的吗?如果有，分区是如何定义的呢?
* 每张表中都有哪些列?
* 每张表中可用的索引都有哪些?
* 每张表及其中的列和索引的统计信息都是什么?
* 某些列上有直方图信息吗?

统计信息为优化器描绘出了各种访问和联结数据的方法是如何实现的蓝图。优化器能够知道的信息你也能够知道。你所需要能够做的事情就是从数据字典中查询信息。在你查看统计信息的时候需要记住的一点是统计信息可能能够也可能不能准确地表示你的数据。如果统计信息过时缺失或者没有被很好地收集，可能就会画出错误的蓝图。优化器只能知道统计信息所告诉它的与之不同的是，你具有判断统计信息是否有意义的能力。例如，你的某张表中的日期列的高位值是在6个月前，你很快就能看到这一点并知道这些行与当前日期的值同时存在。这种视觉观察可以帮助你来判断统计信息是否需要更新。但如果没有看到这些内容你就不会知道它们。你必须经常问的一个关键问题就是统计信息是否准确地反映了你的数据情况。它提供了一个来源，让你可以验证可用的统计信息是多具有代表性的。

有了这些信息，你几乎可以回答所有关于数据的问题。如果这些统计信息是来自于将要执行你所写的SQL语句的生产式数据库中就最好了。如果你的开发数据库没有生产库统计信息的副本，要求将生产式数据库的统计信息导入到开发数据库中是个不错的主意，使得优化器可以依据尽可能地以接近生产式数据库的信息来规划执行计划。即使两种环境中的数据并不匹配，也要记住优化器是使用统计信息来决定执行计划的。

既然你已经得到了统计信息，你可以使用这些信息来提问，以及回答关于你期望优化器对你的SQL做什么的问题。例如，如果你写了一个需要返回某个指定消费者(custid)的所有购买数据的查询，你可能需要知道优化器会估算出查询将会返回多少行数据。有了你所查询到的统计信息，你就能够计算出这个查询估计的返回行数为130行(918843行总数据行数x1/7059唯一值)。你可以看到在cust id列上有索引，因此能够满足这个查询的恰当的访问运算就应该是SALES\_CUST\_BIX索引。当执行这个查询时，你可以通过检查执行计划来验证选择的就是这个运算。

索引统计信息叫聚簇因子。这个统计信息帮助优化器来计算将会访问多少个数据块。基本上，聚簇因子与表中的数据块数目越接近，使用这个索引的时候所需要访问数据块数目的估计值就越少。聚簇因子与表中的数据行数目越接近，所需要访问的数据块数目的估计值就越大。访问的数据块数目越少，使用这个索引的成本就越小，优化器也就越可能为执行计划选择这个索引。因此，你可以检查这个统计信息来确定这个索引是多么令人满意的。下列代码清单列出了SALES表的聚簇因子统计信息。

> 索引聚簇因子

{% code lineNumbers="true" %}
```plsql
SELECT T.TABLE_NAME||'.'||I.INDEX_NAME IDX_NAME,
    I.CLUSTERING_FACTOR,T.BLOCKS,T.NUM_ROWS
FROM ALL_INDEXES I,ALL_TABLES T
WHERE I.TABLE_NAME = T.TABLE_NAME
    AND T.TABLE_NAME = 'SALES'
ORDER BY T.TABLE_NAME,I.INDEX_NAME;
```
{% endcode %}

在这个例子中，SALES表所有索引的聚簇因子都具有较低的值(即较接近于表的数据块数)。这恰当地表明在优化器计算使用这些索引的成本时，基于估算的所需访问数据块数目，它们不会增加很大的负担。

除了使用统计信息以外,你可以实际执行一次查询来得到数据的相关情况以及在这个表中需要访问和返回多少行数据。不管语句有多复杂，你可以做优化器会做的事情并将语句分解为单表访问。对于所包括的每张表，只需执行一个或多个查询来计算并查看使用你的SOL语句所要使用的筛选条件会返回多少行数据。正如前面所讨论的，总是去想“分解并征服”。将语句分解为小的部分将有助于你理解如何将它们最有效地组合到一起来得到最终的结果。

## 建立逻辑表达式

一旦你理解了你所写语句需要回答的问题，你就能够写出可以提供答案的SQL语句。通常对于同一个谓语逻辑可能有多种表述方法。能够以易于阅读并且高效的方式构造出查询条件需要你以一种你可能不是很习惯的方式来思考。以面向集合的方式来思考。要想能够最高效地为你的SQL语句构造出查询条件也需要你进行类似的思维方式转换。

关键是学习一些好的布尔逻辑技术，从而你可以不用只依赖于某一种方法来表达条件逻辑。你会发现使用布尔逻辑表达式总是可以做出最高效的执行计划运算选择(一定要对其他替代方法进行彻底地测试)，但最好还是要知道如何构造不同的替代语句，这样可以让你不必局限于某一种方法。 在说条件逻辑的时候，我指的是类似于`“if X ten y”`这样的表达式，其中X和Y都是条件。在一个WHERE子句中，你可能需要有一个类似`if:GetAll <> 1 then empno=:empno`这样的条件。换句话说，如果绑定变量`:GetAll`的输入值为1，那么你需要返回所有行，但如果`:GetAll`不为1，则仅返回empno等于所给定的:empno绑定变量值的数据行。一个表达这个逻辑的WHERE子句编码如下:

```sql
WHERE empno = CASE WHEN :GetAll <> 1 THEN :empno ELSE empno END
```

这个逻辑是可以的，但对我来说还不够直观。你为什么还要检查empno=empno呢?同时这种结构还有另外一些问题。如果需要检查多个列，你就需要多个CASE语句。并且，如果empno为空，这个检查将失败，或者至少给你一个意料之外的结果。

解决的关键是将这个表达式修改为仅使用AND、OR和NOT的正则布尔表达式，从而将你的“`if X then y`”的条件转换为`“(Not X) or Y”`。则上面的WHERE子句变为:

```sql
WHERE (:GetAll = 1) OR (empno = :empno)
```

这个表达式包含的内容是如果:GetAll=1，那么你根本不需要检验表达式的其他部分。必须记住在使用0R条件的时候，如果一个条件的值为真，则整个表达式的值就为真。没有必要再检验表达式的剩余部分。这个“短路”机制使得有一部分代码路径不需要计算，从而节省了时间。这意味着你不需要占用太多的CPU运算周期。只有在优化器选择进行测试的第一个条件为假的情况下你才需要计算表达式中的另一个条件。

尽管在这些例子中并不是在看包含AND条件的表达式，但你可以将类似的思想应用到包含AND谓语的查询中。当使用AND条件的时候，如果第一个条件的值为FALSE，则整个表达式的值就是FALSE。不必再去求解第二个表达式，因为要想整个条件的值为TRUE必须两个条件的值都为TRUE。因此，在你使用AND条件的时候，将值最有可能为FALSE的表达式放在前面是个好主意。这样就可以使第二个表达式的求解被短路,其原因就类似于在0R条件关系中将一个值为TRUE的条件放在前面。

另一个实现这种类型条件表达式的类似方法就是使用一个绑定变量而不是两个。在这种情况你可以说“如果X不为空那么Y=X”。这可以写为:

```sql
WHERE empno = NVL(:empno,empno)
```

这与之前例子中的CASE表达式基本上是一样的，可以转换为:

```sql
WHERE (:empno is null) OR (:empno = empno)
```

在这两种情况下，优化器都会在确定最优的执行计划时陷入两难的境地。原因就是如果你所使用的绑定变量导致比较最终返回了所有的数据行，那么最适合的计划将可能是进行全表扫描。但是，如果你指定的绑定变量最终限制了结果集，那么索引扫描将是最适合的。由于你使用的是绑定变量，每次你执行查询的时候，输入的绑定值都可能会发生变化。因此，优化器必须选择一种能适合这两种情况的执行计划。最有可能的是，最终你会得到使用全表扫描的执行计划。

此外，如果你在一个很大的代码体内部来写SQL语句，例如在PL/SQL存储过程中，尽量在编码语言中使用条件结构而不要将逻辑放在SQL中。你的SQL语句越简单，在语句中需要直接进行处理的条件越少，优化器确定最优执行计划时的复杂性也就越小。

## 小结

问题是写出好的SQL语句过程中非常重要的一部分。你从理解SQL需要回答的问题开始，然后通过问关于数据的问题来形成功能上正确并且性能最优的SQL语句。问好的问题的能力是一个非常具有智慧的习惯，必须要长时间才能养成。你问越多的问题来搞清楚要干什么并进一步增强对此的理解，你写出高质量高性能SQL语句的技能也就会变得越高。
